# UG SaaS — Department and retail extension, 9 October 2026

This source release extends the previous consolidated ERP. It is a staging candidate, not a certification that the live system is production ready. No GitHub push or deployment was made.

## Setup

Follow START-HERE.md for Node, MongoDB replica-set, server/client environment, owner bootstrap and initial ERP cutover. Never use shared default passwords. This release adds `Production & Retail` to the customer sidebar and `Departments` inside Integrated ERP.

1. Owner: open Plans and configure an active Business/Enterprise/custom plan. For all nine downstream departments use maxDepartments >= 9, ERP_CORE plus STITCHING, INWARD, CHECKING, IRONING, PACKING, DISPATCH, WAREHOUSE, SHOP, MARKETING in Modules. Add ERP_SHOP_FLOOR, ERP_FINANCE and ERP_HR if those existing screens are licensed. Set real prices; default seed prices are not market valuations.
2. GST subscription: owner sets plan taxPercent; 0 creates a no-tax subscription invoice. Positive rates require UG_SAAS_GSTIN. Configure supplier legal name, address, state and SAC. Tax applicability/rate and invoice adequacy need accountant review. A GST-registered business should not select zero merely to omit legally applicable tax. No government filing/e-invoice API is implemented.
3. Owner: Create Company, select an active plan, factory details, strong administrator password and enabled departments. Selection must fit plan limit/license. Owner may update departments using Configure departments; this exposes configuration, not customer operational data.
4. Company administrator signs in through its unique `/c/<companyKey>/login`, after email activation. Configure Resend verified domain, API key, EMAIL_FROM and CLIENT_URL. Existing email problems are not fixed by this ERP extension alone.
5. Company admin creates department users. Grant `department.<name>.read` / `.write`. Shop cashiers also require `shop.<masterKey>`; add assigned shop keys in the existing user permission editor after creation. Updated sessions must sign in again. Admins see all shops; ordinary cashiers see only assigned shops.
6. Create core finished-piece variant SKUs (one SKU per colour/size) and RAW/CONSUMABLE accessory SKUs. Piece units accepted at delivery are PCS, PC, PIECE, PIECES.
7. Create stitching master: unique version key, finished SKU and comma-separated operation names. Create packing master: same SKU, material SKU, material quantity and perPieces basis. Ten starting rows plus Add material. `1 perPieces=1` means one material per piece; `1 perPieces=50` consumes one box for every started group of 50 pieces. Actual nonstandard usage is not yet editable.
8. Create WAREHOUSE and SHOP masters with unique short keys.
9. Cutover/handoff: review physical stock and core ledger first. Section delivery draws an existing piece SKU from core CUTTING or FINISHED, reducing that stock and retaining its value. It does not import or mutate historical delivery challans automatically. Fabric/BOM WIP-to-piece conversion must be reconciled separately before handoff; do not insert arbitrary zero-cost finished stock or repeat a production receipt already counted in this flow. Historical fabric/cutting forms remain historical after ERP activation.

## Daily workflow

- Stitching: delivery creates LOT and BND references, DC/order/section, frozen operations and packing master. Advance STITCHING_READY to OP:0, complete each operation with partial quantities; final completion becomes STITCHED. Each child bundle retains its lineage. Operation master edits require a new version key; older lot snapshots do not change.
- Inward: partial STITCHED receipt moves to CHECKING and increments original lot received. `sent - received` remains section pending. REWORK_DONE goes back to CHECKING without decrementing original DC pending a second time.
- Checking: classify any partial available quantity as good/rework/oil/reject. Total cannot exceed stock. Rework -> REWORK_DONE -> CHECKING; oil -> OIL_DONE -> CHECKING. Each return increments cycle. GOOD -> IRONING -> IRONED. Reject remains valued WASTE stock until company-admin-approved disposal records waste expense. Oil-removal labour and stitching rates are not automatically costed here.
- Bundle QR: View/QR displays secure company/factory trace and print. Scan requires login and relevant department/shop access. Split creates another child tag and conserves stock. Tags carry SKU; resolve colour/size using its variant master. Individual garment serials are not generated.
- Packing: IRONED bundles are visible in Packing. Pack consumes the frozen accessories from ACCESSORIES, incorporates their inventory value into packed garments and generates a carton/bundle tag. Insufficient accessories rolls back all changes. One entry creates one carton/bundle; use quantities matching real box capacity and split as needed.
- Dispatch: PACKED -> TRANSIT_WAREHOUSE with warehouse key. Warehouse receipt can be partial; unreceived quantity remains in transit. Warehouse -> TRANSIT_SHOP with shop key; Shop receipt may be partial. Shop stock may return to warehouse or transfer to another shop through a new transit movement. Receipt never automatically writes off shortages.
- Shop: select physical bundle, pieces, unit price, overall discount, GST rate/type, CASH/BANK and optional customer details. Invoice posts cash/bank, revenue, output tax, inventory and COGS together. No GST requires rate zero. GST invoices require factory GSTIN. Actual CGST/SGST/IGST applicability must be reviewed; this is not a tax-rule engine.
- Returns: select sale, quantity and reason. Cannot exceed unreturned sale. Refund uses original payment mode and allocated price/tax/cost; returned goods enter CHECKING, not saleable stock. This records a refund in accounts; it does not execute a card/bank refund API. Repacking returned goods consumes new accessories.
- Marketing: choose days/lead days/safety stock. View net sales, returns, stock, transit and replenishment suggestion. Create a demand request, have a different company administrator approve it. Copy approved demand ID into Integrated ERP WORK_ORDER and choose matching BOM/output SKU. Total unreversed work orders linked to that demand cannot exceed approved pieces. Procurement POs remain separately reviewed. No automatic purchase orders or stockout/promotion forecasting.

## Limits and acceptance before live use

- Tested policy rules, build and anonymous HTTP access; see RELEASE-VALIDATION.md. Real database scenarios are included but skipped without TEST_MONGODB_URI. Run only against disposable staging replica-set infrastructure; tests create and drop generated test databases.
- Must test partial DC inward, repeated oil/rework, concurrent packing/sales, duplicate network retries, role/shop/company isolation, physical QR/print, balances versus journals, sales returns, subscription expiry/renewal, email/provider and encrypted restore using staging data.
- Department-specific workflow entries cannot be reversed through the generic ERP reverse button because that would desynchronise bundles. Checking includes an administrator-only Undo movement screen. Delivery/advance/check/pack/transfer/split can be reversed only while each output remains completely unused; undo downstream entries first. Stock/value and original inward counts are restored transactionally. Sales must use sales returns. Approved shortage adjustment remains unimplemented; never clear transit shortages by inventing a receipt.
- No garment serial scanning, shop offline POS, barcode scanner integration, multi-currency, bank/card capture, statutory payroll, e-invoicing, rack/bin allocation, garment operation labour costing, lead-time optimizer or automatic legacy challan conversion.
- Department dashboards are bounded (10,000 active bundles, 2,000 masters/lots/latest sales). Core planner retains its previous 20,000-balance limit. Long-running production needs archiving/scalability work before these limits are reached.
- Disabled departments and expired subscriptions retain data. Owner does not obtain operational access by provisioning a company or changing its licensed department list. Customer profile updates cannot change entitlements.

This document takes precedence over older milestone documents for these extensions. The release does not claim feature parity with Zoho, Odoo or ERPNext.

## Company list / activation update

Companies list now shows administrator User ID, email and activation-mail status. Click company name or Departments to view selected department access. Owner may resend activation from the list. ACCEPTED means Resend accepted the request, not proof of Gmail delivery. FAILED leaves the company/account intact for a resend; do not create a duplicate company. Missing provider settings/public production CLIENT_URL block provisioning before a company is created.

Admin email is trimmed/lowercased and reserved in the central registry with a unique partial index, including archived registrations. Legacy company-admin email metadata is checked before creating new registrations. Unrecorded legacy admin IDs are resolved from account metadata only for the company list. These changes do not expose operational ERP data to the owner. Automatic Gmail alias/dot consolidation is not implemented. Concurrent uniqueness depends on successful MongoDB index creation; run staging duplicate-create and provider-failure acceptance. Already-existing duplicate administrators are not silently merged/deleted.
